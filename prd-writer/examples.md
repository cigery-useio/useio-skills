## 示例 1：B2B SaaS — 企业协同办公平台

### 用户输入

```
帮我写一个 PRD：我们要做一个企业协同办公 SaaS 平台，类似飞书但面向中型制造企业，核心是任务管理和生产协同。
```

### 工作流路径

**Phase 0（需求澄清）**：
- 第一轮：确认项目类型 → B2B SaaS
- 第二轮（从初始描述已知“中型制造企业”“任务管理和生产协同”，追问 2 个关键问题）：
  - 问：多租户隔离方式？→ 答：行级隔离（tenant_id 字段）
  - 问：计费模式？→ 答：按用户数月付，基础版/专业版/企业版
  - （私有化部署需求在用户后续补充中确认：企业版支持）

**Phase 1（需求分析）**：
- 功能模块：任务管理、生产协同、文档共享、即时通讯、报表
- Non-Goals：本期不做视频会议、OKR 管理
- 复杂度：复杂产品，使用 plan 工具规划结构

**Phase 2（模板撰写）**：
- 读取 `templates/b2b-saas.md` 模板
- 按模板 15 个章节填充内容

**Phase 3（质量校验）**：
- 对照 B2B SaaS 专项检查项（#17-#23）
- 修正：补充等保二级安全要求清单

**Phase 4（交付）**：
- 输出 `docs/prd-enterprise-collaboration.md`
- 生成角色专属摘要

### 关键产出片段

**用户故事示例**：
```
US-01：创建生产任务
- 用户故事：As a 车间主任, I want to 创建生产任务并分配给班组成员 so that 生产计划可追踪可考核
- 优先级：P0
- 验收标准：
  - [ ] 任务标题、关联工单、计划数量、截止时间为必填
  - [ ] 任务分配后，被分配人收到站内通知和企业微信推送
  - [ ] 任务状态变更（待开始/进行中/已完成/已取消）记录操作日志
  - [ ] 车间主任可查看本车间所有任务，班组成员只能查看分配给自己的任务
```

**多租户隔离方案示例**：
```
隔离级别：行级隔离
实现方案：
- 所有业务表增加 tenant_id 字段，类型 bigint，非空
- MyBatis 拦截器自动注入 tenant_id 查询条件，防止跨租户访问
- 对象存储按 tenant_id 分目录：/tenant/{tenant_id}/docs/{file_id}
- Redis 缓存 key 格式：tenant:{tenant_id}:{module}:{key}
- 单元测试覆盖：自动化测试验证租户 A 无法查询租户 B 的数据
```

## 示例 2：内部管理系统 — 采购审批管理系统

### 用户输入

```
帮我写一个 PRD：公司要做一个采购审批系统，替换现在的纸质流程，需要和现有的 ERP 和企业微信对接。
```

### 工作流路径

**Phase 0（需求澄清）**：
- 第一轮：确认项目类型 → 内部管理系统
- 第二轮（从初始描述已知“采购审批系统”“需要和 ERP 和企业微信对接”，追问 2 个关键问题）：
  - 问：核心审批流程有哪些？→ 答：采购申请 → 部门经理 → 财务 → 总经理（>5 万）
  - 问：部署环境？→ 答：内网部署
  - （使用者信息在用户后续补充中确认：采购员、部门经理、财务、总经理）

**Phase 1（需求分析）**：
- 功能模块：采购申请、审批流引擎、供应商管理、采购订单、报表
- Non-Goals：本期不做合同管理、库存管理
- 复杂度：中等，直接进入 Phase 2

**Phase 2（模板撰写）**：
- 读取 `templates/internal-system.md` 模板
- 按模板 15 个章节填充内容

**Phase 3（质量校验）**：
- 对照内部管理系统专项检查项（#24-#30）
- 修正：补充审批流回退规则和代理设置

**Phase 4（交付）**：
- 输出 `docs/prd-procurement-approval.md`

### 关键产出片段

**审批流设计示例**：
```
采购审批流：
  触发条件：采购员提交采购申请单
  审批节点：
    1. 部门经理审批（≤ 24 小时）
    2. 财务审核（≤ 24 小时）
    3. 总经理审批（仅当金额 > 5 万元时触发，≤ 48 小时）
  
  审批操作：同意 / 驳回 / 回退 / 转办
  
  回退规则：
    - 驳回：直接退回给申请人，流程结束
    - 回退：退回上一节点重新审批
  
  超时处理：
    - 超时自动通过企业微信提醒审批人
    - 超过 48 小时未处理，自动转办给审批人的上级
  
  代理设置：
    - 审批人可设置出差/请假期间的代理人
    - 代理人拥有与原审批人相同的审批权限
    - 代理期间的操作记录标注"代理审批"
```

**系统集成方案示例**：
```
| 系统 | 集成目的 | 集成方式 | 数据流向 |
|------|----------|----------|----------|
| 用友 U8 ERP | 采购订单同步 | REST API | 双向 |
| 企业微信 | 消息通知 + SSO | OAuth2 + Webhook | 双向 |

数据同步策略：
  - 采购订单审批通过后，实时推送到 ERP 创建正式采购单
  - ERP 采购单状态变更，每小时同步一次到本系统
  - 同步失败自动重试 3 次，仍失败则告警并人工介入
```

### 用户输入

```
帮我写一个 PRD：我们要建一个电商数据分析平台，把多个渠道的订单数据汇总分析，给运营和管理层看报表。
```

**Phase 0（需求澄清）**：
- 第一轮：确认项目类型 → 数据平台

- Non-Goals：本期不做实时推荐、用户画像标签
- 复杂度：复杂产品，使用 plan 工具规划

**Phase 2（模板撰写）**：
- 读取 `templates/data-platform.md` 模板
- 按模板 14 个章节填充内容

**Phase 3（质量校验）**：
- 对照数据平台专项检查项（#31-#37）
- 修正：补充数据质量规则和血缘追踪方案

**Phase 4（交付）**：

### 关键产出片段

**数据分层架构示例**：
```
| 层级 | 说明 | 存储引擎 | 保留策略 |
|------|------|----------|----------|

| DWD | 清洗标准化后的订单明细 | ClickHouse | 2 年 |

## 示例 4：API 平台 — 物流轨迹查询 API

### 用户输入

```
帮我写一个 PRD：我们要开放物流轨迹查询 API 给第三方电商平台接入，需要完整的开发者门户和限流配额管理。
```

### 工作流路径

**Phase 0（需求澄清）**：
- 第一轮：确认项目类型 → API 平台
- 第二轮（从初始描述已知“物流轨迹查询 API”“第三方电商平台接入”“开发者门户和限流配额管理”，追问 2 个关键问题）：
  - 问：认证方式？→ 答：OAuth 2.0 授权码模式
  - 问：预计调用量级？→ 答：日均 100 万次，约 15 个接口
  - （版本管理需求在用户后续补充中确认：需要，同时支持 v1/v2）

**Phase 1（需求分析）**：
- 功能模块：API 网关、认证授权、限流配额、开发者门户、监控告警
- Non-Goals：本期不做 SDK 自动生成、社区论坛
- 复杂度：中等偏复杂

**Phase 2（模板撰写）**：
- 读取 `templates/api-platform.md` 模板
- 按模板 15 个章节填充内容

**Phase 3（质量校验）**：
- 对照 API 平台专项检查项（#38-#44）
- 修正：补充 API 错误码规范和灰度发布策略

**Phase 4（交付）**：
- 输出 `docs/prd-logistics-api.md`

### 关键产出片段

**API 设计规范示例**：
```
URL 规范：
  GET    /api/v1/tracks/{tracking_no}          # 查询物流轨迹
  GET    /api/v1/tracks                         # 批量查询轨迹
  GET    /api/v1/outlets                        # 查询网点列表
  POST   /api/v1/orders                         # 创建物流订单
  GET    /api/v1/orders/{order_id}              # 查询订单详情

统一响应格式：
  {
    "code": 0,
    "message": "success",
    "data": {
      "tracking_no": "SF1234567890",
      "status": "in_transit",
      "tracks": [
        { "time": "2026-08-20 10:00:00", "location": "深圳转运中心", "event": "已到达" },
        { "time": "2026-08-20 08:00:00", "location": "广州集散中心", "event": "已发出" }
      ]
    },
    "requestId": "a1b2c3d4-e5f6"
  }

错误码：
  0    : 成功
  1001 : 参数校验失败
  1002 : 认证失败（无效的 Access Token）
  1003 : 权限不足（未授权该 API）
  2001 : 运单号不存在
  2002 : 运单号格式错误
  4290 : 请求频率超限
  5001 : 服务暂时不可用
```

**限流配额策略示例**：
```
| 维度 | 限流规则 | 说明 |
|------|----------|------|
| 全局 | 5000 QPS | 平台总并发上限 |
| 应用级 | 500 QPS/应用 | 单应用并发上限 |
| API 级 | 200 QPS/API | 单 API 并发上限 |

配额管理：
  | 配额类型 | 计量方式 | 超额处理 | 重置周期 |
  |----------|----------|----------|----------|
  | 日调用量 | 次数/天 | 返回 4290 错误码 | 每日 0 点 |
  | 月调用量 | 次数/月 | 返回 4290 + 邮件通知 | 每月 1 日 |

限流算法：令牌桶（Redis + Lua 脚本实现分布式限流）
```

## 示例 5：2C 移动端 — 健身打卡小程序

### 用户输入

```
帮我写一个 PRD：我们要做一个健身打卡小程序，用户可以记录运动、分享打卡到朋友圈、参加挑战赛。

**Phase 0（需求澄清）**：
- 第一轮：确认项目类型 → 2C 移动端（Agent 根据初始描述"小程序"判断为 2C，使用选项组合 B 提问：1.2C 移动端 2.2C Web 产品 3.B2B SaaS 4.内部管理系统，用户选择 1）

  - 问：变现模式？→ 答：初期免费，后期会员订阅（专属训练计划）
  - （产品形态在初始描述中已明确：微信小程序）

**Phase 1（需求分析）**：
- 功能模块：运动记录、打卡分享、挑战赛、排行榜、会员体系
- Non-Goals：本期不做社交动态 Feed、不做 AI 教练
- 复杂度：中等，直接进入 Phase 2

**Phase 2（模板撰写）**：
- 读取 `templates/2c-mobile.md` 模板
- 按模板 15 个章节填充内容

**Phase 3（质量校验）**：
- 对照 2C 移动端专项检查项（#45-#50）

**Phase 4（交付）**：
- 输出 `docs/prd-fitness-checkin.md`

### 关键产出片段

**增长漏斗示例**：
```
| 漏斗阶段 | 关键指标 | 目标值 | 优化策略 |
|----------|----------|--------|----------|
| 获取 | 新增用户数 | 月新增 5 万 | 朋友圈裂变 + 微信搜一搜 ASO |
| 激活 | 首次打卡完成率 | ≥ 60% | 新手引导 + 首次打卡奖励勋章 |
| 留存 | 7 日留存率 | ≥ 35% | 每日推送提醒 + 连续打卡奖励 |
| 变现 | 会员转化率 | ≥ 5% | 7 天免费试用 + 专属训练计划 |
| 推荐 | 分享率 | ≥ 20% | 打卡海报 + 邀请好友双方得积分 |
```

**内容审核机制示例**：
```
审核机制：
  - 机审：阿里云内容安全，图片+文字自动检测（涉黄/涉政/广告）
  - 人审：机审标记为疑似违规的内容，4 小时内人工复核
  - 审核时效：机审 ≤ 30 秒，人审 ≤ 4 小时
  - 违规处理：
    - 轻度：内容删除 + 用户警告
    - 中度：内容删除 + 禁言 7 天
    - 重度：封禁账号
```

## 使用建议

1. **不确定项目类型时**：参考上述示例，选择最接近的场景类型
2. **混合型项目**：选择主要特征对应的模板，从其他模板借用相关章节
3. **参考而非照搬**：示例中的具体数据（如 QPS、数据量）仅为演示，实际撰写时需根据项目真实情况填写
4. **质量校验**：撰写完成后，务必对照 `quality-checklist.md` 中对应项目类型的专项检查项逐项验证
